# Torob Home --- Home Procurement Assistant

> An intent-driven home procurement assistant that turns a user's home
> goal into a structured, purchasable selection of real catalogue
> products.

## 1. Overview

Torob Home is a prototype for a home procurement assistant. It is
deliberately different from a conventional product search or
price-comparison page.

A conventional shopping search starts with a product:

``` text
"washing machine"
        ↓
products → sellers → prices
```

Torob Home also supports that flow, but its distinctive flow starts with
a goal:

``` text
"بازسازی سرویس بهداشتی ۱۲ متری"
        ↓
intent
        ↓
project requirements
        ↓
catalogue subcategories
        ↓
eligible products
        ↓
selection list
        ↓
budget / seller comparison / optimization
```

The core product thesis is:

> The system should understand what the user is trying to accomplish in
> the home, translate that intent into concrete procurement
> requirements, and then source those requirements from a controlled
> product catalogue.

The LLM is used for semantic interpretation and bounded reasoning. It is
not the source of truth for products, prices, sellers, availability, or
monetary calculations.

This repository is a working prototype/demo, not a production
marketplace.

## 2. Product Scope

The application currently supports two primary user intents.

### 2.1 Product search

The user already knows approximately what they want to buy.

Examples:

``` text
یه شیر توالت خوب میخوام
سینک ظرفشویی
دنبال یه ماشین لباسشویی تا ۳۰ تومن میگردم
```

The system should return products from the catalogue, apply explicit
constraints, and expose sellers/offers where available.

Product search is intentionally not routed through the LLM when the
query is already a sufficiently clear product query.

### 2.2 Project / need search

The user describes a job, room, or outcome instead of naming products.

Examples:

``` text
بازسازی سرویس بهداشتی ۱۲ متری
اتاق خواب ۱۲ متری رو می‌خوام تغییر دکوراسیون بدم
برای آشپزخونه ۱۰ متری چی لازم دارم؟
```

The system extracts the project structure and derives procurement
requirements.

For example, a bathroom renovation can result in requirements such as
sanitary fixtures, faucets, mirror, finishing materials, waterproofing,
lighting/ventilation, or plumbing work depending on the stated goal and
semantic decomposition.

A requirement is not a product. It is a statement of what is needed to
accomplish the project.

### 2.3 Selection list

The application uses a **selection list**, not a shopping cart.

The selection list represents products the user has explicitly chosen
for further comparison or planning.

It is not:

-   a checkout cart,
-   a payment basket,
-   a quantity-based purchasing system,
-   an automatic recommendation bucket.

Products are added and removed explicitly. Package actions can add or
remove the actual products currently represented by a project
recommendation set.

There is no product-level quantity field.

Project requirement quantity is different and remains valid. It
describes how much of a project requirement is needed, not how many
catalogue items the user is purchasing.

## 3. Core Product Principles

### 3.1 Intent first, catalogue truth second

The semantic layer answers:

-   What did the user ask for?
-   Is this a product query or a project query?
-   What room/project context was stated?
-   What requirements follow from the described goal?
-   What explicit constraints did the user provide?

The catalogue layer answers:

-   Which products exist?
-   Which subcategory does a product belong to?
-   Which rooms/use cases is it suitable for?
-   Which offers and sellers exist?
-   What are the prices?
-   What products are complementary or alternative?

These responsibilities must not be mixed.

### 3.2 The LLM cannot invent catalogue facts

The interpretation schema contains no product, seller, offer, or price
field.

The LLM may produce:

``` text
intent
project type
room
area
goal
requirements
search terms
quality/budget constraints
```

It does not produce an authoritative product record.

When an LLM is used for project reasoning, it receives a bounded
candidate set generated by the backend. It can select among those
candidates, but it cannot expand the catalogue.

Every proposed product is validated against the candidate set before it
can affect the result.

### 3.3 Hard constraints are deterministic

The backend owns facts that must be correct:

-   catalogue membership,
-   category/subcategory,
-   room eligibility,
-   project applicability,
-   budget hard limits,
-   product IDs,
-   prices,
-   seller offers,
-   selection-list state,
-   candidate generation.

The LLM is not trusted to enforce these facts.

### 3.4 No silent mutation

Reasoning may recommend a replacement or optimization, but it does not
silently replace a user's explicit selection.

The user must confirm a replacement before the selection list changes.

Likewise, recommendations do not automatically enter the selection list.

## 4. Request Routing

The search entry point uses a product-first strategy.

``` text
Search query
    │
    ▼
Deterministic product matcher
    │
    ├── clear/high-confidence product match
    │        │
    │        └── Product search
    │             0 LLM calls
    │
    └── not clearly a product
             │
             ▼
        LLM interpretation
             │
             ├── product_search
             ├── project_search
             └── unknown
```

The purpose of the deterministic matcher is not to understand every
possible query.

It only needs to confidently prove that a query is a direct product
search.

False negatives are acceptable: an ambiguous product query can fall
through to interpretation.

False positives are more dangerous because they bypass semantic
interpretation.

The matcher uses the existing catalogue vocabulary and product-search
matching logic. It does not introduce:

-   a second semantic model,
-   embeddings,
-   an external search engine,
-   a hardcoded Persian phrase dictionary,
-   query-specific routing rules.

This keeps routing cheap and predictable.

------------------------------------------------------------------------

## 5. Interpretation Architecture

For queries that are not confidently product-first, the application
makes one interpretation call.

The conceptual output is:

``` json
{
  "intent": "project_search",
  "category": null,
  "project": {
    "type": "renovation",
    "room": "سرویس بهداشتی",
    "room_token": "bathroom",
    "area_m2": 12,
    "goal": "بازسازی سرویس بهداشتی",
    "constraints": [],
    "requirements": []
  },
  "search": null,
  "constraints": {
    "quality": "medium",
    "budget": null,
    "notes": []
  },
  "constraint_kind": "QUALITY",
  "confidence": 0.99,
  "explanations": []
}
```

The exact schema is enforced by Pydantic and JSON Schema.

Supported intents are:

-   `product_search`
-   `project_search`
-   `unknown`

The interpretation layer should preserve facts supplied by the user
rather than inventing project facts.

Requirements are the deliberate exception: project intent requires
semantic decomposition into the things that must be procured to
accomplish the stated goal.

### 5.1 Canonical quality values

User language is normalized into a small canonical vocabulary:

  User wording                     Canonical value
  -------------------------------- -----------------
  اقتصادی / معمولی / پایه          `low`
  متوسط                            `medium`
  خوب / باکیفیت                    `high`
  لوکس / بسیار باکیفیت / پریمیوم   `ultra`

The API schema stays canonical; the model is responsible for mapping
natural Persian wording into the enum.

### 5.2 Strict structured output

The LLM client requests JSON Schema output and validates the response
with strict Pydantic models.

Models use `extra="forbid"`.

A response that is semantically reasonable but structurally invalid is
still rejected.

This is intentional: downstream code must never operate on an uncertain
interpretation shape.

The prompt explicitly describes the root hierarchy because a previous
model response incorrectly placed root fields such as `search`,
`constraints`, `confidence`, and `explanations` inside `project`.

## 6. Requirement Model

Project requirements are semantic procurement needs, not catalogue
products.

A requirement contains concepts such as:

``` json
{
  "description": "شیرهای سرویس بهداشتی",
  "terms": ["شیر", "توالت"],
  "quantity": 1,
  "required": true,
  "quality_min": "medium"
}
```

Requirements must follow these rules:

-   describe a kind of thing, not a specific product;
-   do not contain product IDs;
-   do not contain seller names;
-   do not contain model names;
-   do not contain catalogue prices;
-   do not depend on current catalogue availability;
-   avoid umbrella terms such as "تجهیزات" or "لوازم";
-   remain meaningful even when the catalogue cannot satisfy them.

A missing catalogue match is reported as an unmet requirement. It is not
silently deleted and it is not replaced with an unrelated product.

### 6.1 Requirement quantity vs product quantity

This distinction is important.

`requirement.quantity` answers:

> How much of this project requirement is needed?

It does not answer:

> How many units of this exact product should I purchase?

The latter does not belong in the current product/selection model.

## 7. Catalogue

The catalogue is the application's source of product truth.

The canonical enriched catalogue currently contains 70 manually selected
products across:

-   bathroom
-   kitchen
-   furniture
-   appliances

The products are enriched once offline with structured metadata.

The enrichment includes:

``` text
rooms
product_roles
use_cases
project_types
space_fit
styles
features
search_terms
complementary_subcategories
alternative_subcategories
```

The catalogue is not enriched dynamically during a request.

### 7.1 Why the catalogue is enriched

Natural-language project intent cannot be matched reliably using only
raw product names.

For example, a bed may have implications for:

-   sleeping,
-   bedroom,
-   storage,
-   small-space use,
-   specific project types.

Those semantics are captured once in canonical metadata rather than
rediscovered by an LLM on every request.

### 7.2 Catalogue source abstraction

The application separates catalogue access from business logic:

``` text
ProductSource
├── LocalJsonProductSource
└── TorobMcpProductSource
```

Configuration selects the source:

``` env
PRODUCT_SOURCE=local
TOROB_MCP_URL=https://torob-mcp.sajjadbayatani.workers.dev/mcp
```

or:

``` env
PRODUCT_SOURCE=torob_mcp
```

The source is responsible for supplying catalogue data. It is not
responsible for:

-   intent interpretation,
-   requirement generation,
-   ranking,
-   project reasoning,
-   optimization decisions.

The local enriched catalogue remains the semantic reference for project
matching.

## 8. Requirement → Subcategory Matching

This is a deterministic backend step.

A requirement produces short semantic terms. The matcher resolves those
terms against catalogue subcategory vocabulary.

The system intentionally avoids loose substring matching because
substring matching caused false positives such as:

``` text
مبل → مبلمان
```

and missed semantically related wording such as:

``` text
میز تحریر ↔ میز کار
```

The matcher instead works with normalized words and catalogue-derived
vocabulary.

A term counts as evidence when:

1.  the catalogue offers that word as a valid entry point for a
    subcategory, and
2.  the word is not shared by too many subcategories.

This prevents broad words from becoming accidental universal evidence.

### 8.1 Room words are not product evidence

This was an actual regression and is now an explicit invariant.

For example:

``` text
آینه سرویس بهداشتی
```

contains the room words `سرویس` and `بهداشتی`.

Those words are not evidence that the requirement is a mirror.

The room is already handled through `RoomScope`.

The matcher therefore removes room words from product-term scoring.

Without this rule, `آینه سرویس بهداشتی` became an unusually strong
vocabulary match because it was the only bathroom subcategory label
containing the room name. Plumbing and lighting requirements could
consequently resolve to bathroom mirrors.

The corrected model is:

``` text
room → RoomScope
requirement terms → product evidence
```

not:

``` text
room + requirement terms → product evidence
```

A requirement containing only room words therefore produces no product
match.

## 9. Candidate Generation

Once subcategories are resolved, the backend generates candidate
products.

Candidate generation applies hard deterministic filters such as:

-   project room,
-   product role,
-   project type,
-   space fit,
-   quality constraints where product data supports them,
-   budget constraints,
-   actual catalogue membership,
-   product availability/purchasability.

The backend never asks the LLM to search the full catalogue.

The LLM receives only the bounded candidates relevant to the current
decision.

This keeps prompts smaller and makes hallucinated products structurally
difficult.

### 9.1 Budget

Budget is a hard constraint for product selection where explicitly
supplied.

For example:

``` text
دنبال یه ماشین لباسشویی تا ۳۰ تومن میگردم
```

must not return a washing machine priced above 30,000,000 Toman merely
because it has a high textual relevance score.

Structured constraints must dominate generic token matching.

Money is represented as integer Toman values and calculated on the
backend.

------------------------------------------------------------------------

## 10. Complementary Products

Complementary relationships are catalogue data.

They are not invented by the reasoning model.

A complementary product must:

-   come from a declared catalogue relationship,
-   belong to a different subcategory,
-   satisfy the relevant room/project filters.

An alternative is not a complement.

For example:

``` text
same subcategory → alternative
different declared complementary subcategory → complement
```

The current implementation may generate multiple complement candidates
when a requirement resolves to multiple subcategories. This is an
acknowledged optimization area rather than a reason to weaken catalogue
correctness.

------------------------------------------------------------------------

## 11. Project Reasoning

The LLM is used only after deterministic candidate generation.

Conceptually:

``` text
project
  +
requirements
  +
bounded candidates
  +
constraints
  ↓
reasoning model
  ↓
structured proposal
  ↓
backend validation
  ↓
final selections
```

The reasoning model may:

-   select among candidates,
-   explain why a candidate fits,
-   compare trade-offs,
-   propose a better candidate under a changed budget or constraint.

It may not:

-   invent product IDs,
-   invent sellers,
-   invent prices,
-   search the catalogue,
-   override hard constraints,
-   mutate user selections silently.

### 11.1 One reasoning call per decision

The goal is not to ask the LLM to do every step.

Deterministic code should do deterministic work first.

If a requirement has only one valid candidate, there is no meaningful
ranking decision to delegate.

When a real choice exists, one bounded reasoning call is used.

This also controls cost and latency.

------------------------------------------------------------------------

## 12. Recalculation and Optimization

There are three distinct situations.

### New query

``` text
query
 → interpretation
 → deterministic requirement/candidate generation
 → reasoning
```

Target:

``` text
1 interpretation call
1 reasoning call
```

when reasoning is actually needed.

### Same project, changed constraints

Changing area, quality, budget, or related project parameters should
reuse the existing project interpretation.

``` text
existing interpretation
 → deterministic recalculation
 → reasoning
```

There is no reason to interpret the same natural-language request again.

### Selection optimization

Optimization works on the current selection list and project context.

It must not send the original query back through interpretation.

``` text
existing project
+
current selection
+
new optimization constraints
 → deterministic candidates
 → one optimization reasoning call
 → proposal
 → user confirmation
```

Optimization is therefore not another search.

It is a bounded decision over an existing project and selection state.

No silent product replacement occurs.

------------------------------------------------------------------------

## 13. Selection List Semantics

The selection list is product-ID based and idempotent.

Properties:

-   adding the same product twice does not create duplicate entries;
-   removing a product removes that product explicitly;
-   package selection operates on the actual product IDs in the current
    recommendation set;
-   partial selection is supported;
-   only products with catalogue matches can be selected;
-   project requirements remain independent from selection-list state;
-   optimization proposes changes but does not silently apply them.

The frontend uses the terminology:

-   افزودن به لیست انتخاب‌ها
-   حذف از لیست انتخاب‌ها
-   در لیست انتخاب‌ها
-   لیست انتخاب‌های من
-   بهینه‌سازی انتخاب‌ها

The concept is intentionally not named "cart".

## 14. Product Detail

Product detail is about the product itself and its available sourcing
information.

It includes:

-   product identity,
-   category/subcategory,
-   visual information,
-   structured attributes,
-   price,
-   seller offers,
-   similar products.

"Similar products" are alternatives within the same product context.

The UI does not need a "complementary products" section on the product
detail page. Complementary relationships remain useful internally for
project reasoning and optimization.

Major domains:


Supporting infrastructure:

``` text

```

The `app/catalog` package is intentionally separate from HTTP domains.
It is the catalogue/data layer: indexing, matching, selection, source
access, projections, and catalogue relationships.

HTTP domains orchestrate application behavior and shape API responses.

## 16. Database Responsibility

PostgreSQL stores application-owned state.

It does not need to become the source of truth for the captured
catalogue.

The catalogue is kept as versioned data because it is:

-   inspectable,
-   diffable,
-   reproducible,
-   easy to replace,
-   suitable for a demo dataset.

The database is used for state such as:

-   projects/analyses,
-   selection lists,
-   selection items,
-   project-related application state,
-   other persistent application data.

This separation prevents product truth from being accidentally modified
through ordinary application state.

------------------------------------------------------------------------

## 17. LLM Client Contract

The LLM client is centralized.

Conceptually:

``` python
chat_json(system, user, schema_model)
```

Responsibilities include:

-   OpenAI-compatible API communication,
-   JSON Schema response format,
-   Pydantic validation,
-   timeout handling,
-   truncation detection,
-   structured error reporting,
-   bounded retry behavior.

A model response that ends with:

``` text
finish_reason = length
```

is treated as a truncation failure, not as valid JSON to be guessed or
repaired optimistically.

### 17.1 Model selection

The model is configured explicitly:

``` env
LLM_MODEL=...
```

There is no hidden model fallback.

This is deliberate because model behavior matters to structured-output
adherence and reasoning-token consumption.

Changing the model is therefore an architectural/runtime decision, not a
cosmetic configuration change.

## 18. Frontend Architecture

The frontend is:

-   Vue 3
-   TypeScript
-   Vite
-   Tailwind CSS
-   Pinia
-   Persian-first RTL UI

The frontend communicates with the backend through a dedicated API
layer.

Shared state is kept in Pinia only when it is genuinely cross-view
state, including:

-   search state,
-   catalogue state/cache,
-   selection-list state.

Component-local interaction state stays local.

### 18.1 Thinking States

The search UI contains a Thinking States component.

The component is presentational:

``` text
states
activeIndex
visible
```

It does not own network requests.

The parent search flow maps states to the actual request lifecycle.

There are no fake timers that advance the UI while the backend is still
processing.

If an LLM request takes 30 seconds, the corresponding state remains
active for those 30 seconds.

The animation is visual feedback, not a simulated progress bar.

## 19. Design System

The UI is Persian-first and RTL.

The design system uses:

-   Material Design 2 as the interaction/design reference,
-   centralized theme tokens,
-   Vazirmatn/appropriate Persian typography,
-   logical CSS properties,
-   Persian number formatting,
-   Toman currency formatting.

The frontend should not introduce arbitrary component-level colors,
radii, shadows, or animation durations when a design token exists.

Accessibility and reduced-motion behavior are considered for animated
UI.

``` text
       ↓

       ↓
```

The enriched catalogue is a committed, reviewable artifact.

This is important because catalogue vocabulary directly influences
deterministic matching. A vocabulary change is therefore a semantic
product change and should be reviewable like code.

## 22. Known Limitations

### Partial catalogue coverage

The catalogue does not cover every material or service required by a
real renovation project.

For example, some requirements such as tiles, waterproofing, plumbing,
lighting, or paint may remain unmet.

The correct behavior is to expose the unmet requirement rather than
substitute an unrelated product.

### Quality metadata

Product quality metadata is limited. A user's requested quality level
can be normalized, but a product should not be assigned a quality score
that the catalogue does not actually support.

### Cost estimates

Project totals are product/material estimates.

They are not contractor estimates and do not include:

-   labor,
-   installation,
-   contractor margin,
-   scheduling,
-   wastage unless explicitly modeled,
-   logistics unless explicitly modeled.

### Catalogue scale

The current in-process matcher is appropriate for a small canonical
catalogue.

At much larger scale, the catalogue boundary can move behind PostgreSQL
search facilities or a dedicated search engine without changing the
project/LLM architecture.

### Model variability

Structured-output adherence and reasoning efficiency vary by model.

A model that spends its generation budget on reasoning or narration can
still fail to return the required JSON.

The system reports this as a model/runtime failure rather than inventing
a result.

## 23. Engineering Principles

The following principles guide further work:

1.  **Deterministic before probabilistic.**
2.  **Catalogue truth before model output.**
3.  **Hard constraints are enforced by code.**
4.  **LLMs operate on bounded context.**
5.  **Interpretation and product selection are separate
    responsibilities.**
6.  **Project requirements are not products.**
7.  **Product quantity is not part of the current selection model.**
8.  **User selections are never silently mutated.**
9.  **A missing catalogue match remains visible as an unmet need.**
10. **No hardcoded query-specific semantic mappings.**
11. **No extra model call when deterministic logic can answer the
    question.**
12. **Do not solve token problems by blindly increasing token budgets.**
13. **Prompt changes should preserve schema and architectural
    boundaries.**
14. **Tests should protect invariants and properties, not merely today's
    exact examples.**
15. **Small focused changes are preferred over cross-layer rewrites.**

## 27. Status

This is an evolving technical prototype.

The important architectural boundary is already established:

``` text
User language
     ↓
semantic interpretation
     ↓
structured project/search intent
     ↓
deterministic catalogue resolution
     ↓
bounded candidate set
     ↓
optional LLM reasoning
     ↓
validated user-facing result
```

The system is intentionally designed so that adding more products, more
catalogue sources, better matching, or a better reasoning model does not
require handing catalogue authority to the LLM.
