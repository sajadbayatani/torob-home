# ترب خونه — Torob-Home

**سامانهٔ خرید خانه بر پایهٔ نیت.** شما می‌گویید در خانه‌تان می‌خواهید **چه کاری**
انجام شود — نه اینکه چه چیزی می‌خواهید بخرید — و سامانه آن را به برنامه‌ای
هزینه‌شده و قابل‌تأمین تبدیل می‌کند.

**[English version — نسخهٔ انگلیسی](README.md)**

```
یک جمله → نیت → نیازها → محصولات کاتالوگ → لیست انتخاب‌ها → بودجه و فروشنده‌ها
```

> **این یک پروژهٔ نمایشی (Demo) است.** کاتالوگ شامل **۷۰ قلم محصول واقعی** است که از
> [ترب](https://torob.com) — فروشگاه اینترنتی ایرانی — برداشت شده و برای هر قلم
> حداکثر **۵ پیشنهاد فروشنده** ثبت شده است. هر چیز دیگری که سامانه تولید می‌کند —
> نیازها، برآوردها و تحلیل پروژه — تولیدشده است و API هم به‌جای وانمود کردن،
> همین را اعلام می‌کند.

**دو زبان، یک کدبیس.** این سند فارسی است؛ [README.md](README.md) همان سند به
انگلیسی است. خودِ برنامه فارسی‌محور و در تمام بخش‌ها راست‌به‌چپ است.

## ۱. برنامه چه می‌کند

سه جریان، همگی از صفحهٔ اصلی و بدون هیچ آماده‌سازی:

**جست‌وجوی محصول** — `یه شیر توالت خوب میخوام`
چیز را توصیف می‌کنید. مفسر تشخیص می‌دهد که منظورتان محصول بوده، کاتالوگ کارت‌های
یکدست‌شده را برمی‌گرداند و هر کارت دلیلش را با خود دارد — کدام از کلمات شما تطابق
یافت و چرا. با باز کردن هر محصول، جدول کامل فروشنده‌ها، مشخصات فنی و
**قطعاتی که همراهِ آن می‌آیند** را می‌بینید؛ هر کدام با دلیلی مشخص.

**جست‌وجوی پروژه** — `بازسازی سرویس بهداشتی ۱۲ متری، کیفیت متوسط`
یک **کار** را توصیف می‌کنید. مفسر `project_search` برمی‌گرداند و نیمهٔ دشوار کار
شروع می‌شود: مدل **نیازهای** پروژه را می‌نویسد — آنچه برای تمام شدن این کار باید
تهیه شود، چیزی که کاربر هرگز برشماره است. این نیازها در کاتالوگ به محصولات
مشخص تبدیل می‌شوند و شما فهرست نیازها، پیشنهاد برای هر ردیف، فهرست نیازهای
برآورده‌نشده و برآورد هزینهٔ کل پروژه را می‌گیرید.

**بهینه‌سازی بودجه** — از هر دو صفحه، با یک دکمه
پروژه و لیست انتخاب‌های فعلی را با هم و بر اساس همان اعدادی که همین حالا وارد
کرده‌اید دوباره ارزیابی می‌کند، سپس نتیجه را با هر جابه‌جایی و هزینهٔ کیفیت آن به
صورت پیش از ← هدف ← پس از نشان می‌دهد.

### چرا جریان پروژه مهم‌ترین بخش است

جست‌وجوی محصول مسئلهٔ حل‌شده‌ای است: پرسش دارید، کاتالوگ هم دارید. جریان پروژه
پرسشی ندارد. `بازسازی سرویس بهداشتی` اصلاً نامی از محصول نمی‌برد — یک اتاق و یک
عمل را نام می‌برد. پس باید کسی تصمیم بگیرد که بازسازی سرویس بهداشتی یعنی
عایق‌کاری، لوله‌کشی، لوازم بهداشتی، آینه، روشنایی و رنگ؛ و اینکه برای این پروژه
حدود ۳۹ متر مربع کاشی لازم است. همین تصمیم، محصولِ ماست.

## ۲. قاعده‌ای که همه‌چیز را شکل می‌دهد

> **لایهٔ تفسیر فقط ساختار تولید می‌کند.**
> محصول، فروشنده، قیمت، موجودی و رابطهٔ میان محصولات همیشه از کاتالوگ خوانده
> می‌شوند — توسط مدل یا کدِ پشت آن.

این یک قرارداد نیست؛ ساختاری است:

- مدل `InterpretedIntent` در `backend/app/domains/search/schemas.py` **هیچ فیلدی**
  برای محصول، پیشنهاد، قیمت یا فروشنده ندارد. مفسر اصلاً نمی‌تواند محصول ساختگی
  را نمایش دهد، چون جایی برای نگه‌داشتنش وجود ندارد.
- هر مدل ورودی و خروجی از `StrictModel` با `extra="forbid"` ارث می‌برد. کلید
  ناشناخته یعنی خطای اعتبارسنجی، نه بی‌تفاوتی.
- پاسخ مدل علاوه بر این با یک اسکیمای سخت‌گیرانهٔ Pydantic و با
  `response_format=json_schema` اعتبارسنجی می‌شود.
- هیچ‌گاه مبلغ نهایی توسط مدل تولید نمی‌شود. همهٔ پول‌ها روی سرور و به‌صورت عدد
  صحیح، به تومان محاسبه می‌شود.
- اگر اسلاگی که مدل برگرداند در کاتالوگ نباشد، به `missing_categories` منتقل و
  هرگز جست‌وجو نمی‌شود.

خطایی که این طراحی حذف می‌کند مشخص است: مدلی که اجازهٔ نام‌بردن از محصولات داشته
باشد، با همان اطمینان نام محصولات را می‌برد، چه وجود داشته باشند چه نه. همهٔ
آنچه در ادامه می‌آید، پیامدِ ناممکن‌کردنِ این رفتار است، نه کم‌احتمال‌کردنش.

## ۳. معماری

یک **تک‌واحد ماژولار (Modular Monolith)**: یک بک‌اند، یک فرانت‌اند، یک پایگاه داده.
سه کانتینر.

```
                    ┌─────────────────────────────────────┐
   مرورگر  ────────▶│  فرانت‌اند   Vue 3 · TS · Tailwind  │
                    └───────────────┬─────────────────────┘
                                    │  REST /api/v1  (JSON)
                    ┌───────────────▼─────────────────────┐
                    │  بک‌اند   FastAPI · SQLAlchemy 2    │
                    │                                    │
                    │   search  →  projects  →  basket    │
                    │      │          │           │        │
                    │      └──────────┴───────────┘        │
                    │            کاتالوگ (فایل + API)      │
                    │            llm     (OpenRouter)      │
                    └───────────────┬─────────────────────┘
                                    │
                          ┌─────────▼─────────┐
                          │  PostgreSQL       │  لیست انتخاب‌ها، تحلیل‌ها،
                          │                   │  قالب‌ها، قواعد نیاز
                          └───────────────────┘

                    ┌─────────────────────────────────────┐
                    │  data/catalog/*.json  (فقط‌خواندنی) │  ۷۰ محصول توروب
                    └─────────────────────────────────────┘
```

### ساختار مخزن

```
.
├── backend/                   تک‌واحد ماژولار FastAPI
│   ├── app/
│   │   ├── main.py            کارخانهٔ اپ، هندلر استثنا، شناسهٔ درخواست
│   │   ├── api/v1.py          تجمیع مسیرها + نقاط meta
│   │   ├── core/              تنظیمات، enumهای دامنه، ابزار متن فارسی
│   │   ├── db/                موتور، نشست، پایهٔ اعلانی
│   │   ├── catalog/           خودِ کاتالوگ (پایین‌تر توضیح داده شده)
│   │   ├── llm/               کلاینت OpenRouter: chat_json، اسکیما، خطاها
│   │   ├── seed/              دادهٔ نمایشی قطعی + خط فرمان
│   │   └── domains/
│   │       ├── catalog/       HTTP: محصولات، facetها، دسته‌ها، برندها

│   │       ├── search/        HTTP + موتور تفسیر
│   │       ├── projects/      HTTP + تحلیل پروژه و استدلال
│   │       └── basket/        HTTP + لیست انتخاب‌ها و بهینه‌ساز
│   ├── alembic/               مهاجرت‌ها
│   └── tests/                 unit / api / ابزار ردیابی دستی
├── frontend/                  اپ تک‌صفحه‌ای Vue 3 + TypeScript
│   ├── src/
│   │   ├── api/               تنها جایی که HTTP می‌زند

│   └── tests/                 vitest + @vue/test-utils
├── data/
│   ├── raw/                   برداشت‌های دست‌نخوردهٔ جست‌وجوی توروب
│   ├── product-pages/         صفحه‌های محصول، یکی برای هر قلم
│   └── catalog/               کاتالوگ غنی‌شده‌ای که برنامه می‌خواند
├── scripts/                   build_catalog.py · add_offers.py
├── docs/                      یادداشت‌های سیستم طراحی و تاریخچهٔ مهاجرت‌ها
```

`app/catalog/` آگاهانه زیر `app/domains/` نیست. آن لایهٔ داده است، نه دامنه: فایل را
می‌خواند، نمایه می‌سازد، کلمات را به زیر‌دسته‌ها وصل می‌کند و محصولات مکمل را
می‌شناسد. دامنهٔ HTTP بالای سر آن فقط پاسخ‌ها را قالب‌بندی می‌کند.

## ۴. خط لولهٔ کار، از ابتدا تا انتها

این بخش ارزش خواندن دقیق دارد، چون جایی است که طراحی زندگی می‌کند.

```
  ۱. تفسیر              جمله          →  نیتِ تایپ‌شده (اسکیمای سخت‌گیرانه)
  ۲. نیازها             نیت           →  برای تمام شدن کار چه باید خرید
  ۳. نگاشت نیاز         کلمات        →  اسلاگ زیر‌دسته در کاتالوگ
  ۴. ساخت کاندیدا       اسلاگ‌ها     →  محصولات واجد شرایط
  ۵. مکمل‌ها            محصولات      →  آنچه فایل می‌گوید همراهشان می‌آید
  ۶. پرامپت استدلال     همهٔ موارد   →  یک پرسش ساختاریافته
  ۷. مدل استدلال        پرامپت       →  یک پیشنهاد (اعتبارسنجی و بازبینی می‌شود)
  ۸. انتخاب نهایی       پیشنهاد      →  پذیرفته‌شده‌ها، با توضیح رد‌شده‌ها
```

### ۱. تفسیر

یک فراخوانی مدل. پرامپت، تاکسونومی واقعی کاتالوگ را حمل می‌کند — اتاق‌ها،
زیر‌دسته‌ها به‌همراه تعدادشان، برندها — و اسکیما سخت‌گیرانه است. سه نیت:
`PRODUCT_SEARCH`، `NEED_SEARCH`، `UNKNOWN`.

پرامپت مجبور شد ساختار خروجی خودش را یاد بگیرد. یک‌بار مدل `search`،
`confidence` و `explanations` را *درون* `project` برگرداند؛ چون اسکیما کلید اضافه را
رد می‌کند، تفسیری که از نظر معنایی بی‌عیب بود به‌عنوان خطای اعتبارسنجی دور ریخته
شد. پرامپت اکنون سلسله‌مراتب خروجی را صریح بیان می‌کند، دو فیلد متفاوت
`constraints` را از هم جدا نام می‌برد، و فقط و فقط یک شیء JSON بدون استدلال
پیرامونش می‌خواهد.

### ۲. نیازها

برای یک پروژه، مدل فهرست خریدی را می‌نویسد که کاربر هرگز به زبان نیاورده است.
قواعدی که باید رعایت شود در پرامپت آمده و با آزمون‌ها تضمین شده‌اند:

- نیازها **برگرفته از نتیجه‌اند**: آنچه برای رسیدن به نتیجه‌ای که کاربر توصیف
  کرده باید تهیه شود.
- **واژهٔ چتری ممنوع.** «تجهیزات» نیاز نیست؛ اجزایش نیاز است.
- در نیاز، نام برند، مدل، فروشنده، قیمت یا شناسهٔ کاتالوگ نمی‌آید. نیازها
  **گونه‌ای از چیزها** را نام می‌برند، هرگز محصول مشخصی را.
- موجود بودن در کاتالوگ ملاک نیست — نیازِ بی‌محصول هم نیاز است و برآورده‌نشده
  گزارش می‌شود.
- `quantity` **مقدارِ پروژه** است («این کف چند متر مربع کاشی می‌خواهد»)، هرگز
  مقدار خرید. این تمایز بار‌بر است و آزمون مستقل دارد.

### ۳. نگاشت نیاز به زیر‌دسته

نیمهٔ دیگرِ «مدل می‌فهمد، بک‌اند نگاشت می‌کند». یک نیاز کلمه می‌آورد؛ کاتالوگ
می‌داند هر زیر‌دسته را با چه کلماتی نام می‌برد. هر دو به کلمه تقلیل می‌یابند و
**کلمه‌به‌کلمه** تطبیق داده می‌شوند.

تطبیق زیررشته‌ای چیزی است که جایگزین شد و دو خطا می‌ساخت: «مبل» با «مبلمان»
تطابق می‌کرد و «میز تحریر» در برابر «میز کار» شکست می‌خورد. هر دو آزمون دارند.

کلمه تنها زمانی شاهد است که فایل آن را به‌عنوان راهی *به داخل* آن زیر‌دسته عرضه
کند (برچسبش یا یک عبارت جست‌وجو) **و** زیر‌دسته‌های زیادی آن را به‌اشتراک
نگذارند. «مبلمان» برچسب دسته روی هر هشت زیر‌دستهٔ اثاثیه است، پس شاهدِ همهٔ آن‌هاست
و در نتیجه هیچ‌کدام؛ این آستانه از خودِ فایل اندازه‌گیری می‌شود، نه اینکه در کد
فهرست شود.

یک ظرافت ارزش ثبت دارد، چون یک رگرسیون واقعی ساخت: **اتاق شاهد نیست.**
`آینه سرویس بهداشتی` تنها برچسب سرویس بهداشتی است که نام اتاق را می‌نویسد؛ بقیه
کوتاه‌اند (`روشویی`، `توالت`). پس کلمات اتاق واژگانِ همان یک زیر‌دسته با بالاترین
وزن بودند و چون نادر بودند فراوانی‌شان هرگز کنار گذاشته نشد — و نتیجه این شد که
نیازِ لوله‌کشی و روشنایی آینه برگردند. اتاق پیشاپیش توسط `RoomScope.admits` اعمال
شده است؛ خواندن دوبارهٔ آن از کلمات چیزی اضافه نمی‌کند و رتبه‌بندی را وارونه
می‌کند. اکنون کلمات اتاق پیش از امتیازدهی کنار گذاشته می‌شوند.

### ۴–۵. کاندیداها و مکمل‌ها

محصولی پیشنهاد می‌شود که فایل غنی‌شده آن را در یکی از اتاق‌های این پروژه بگذارد،
این نوع کار را مجاز بداند، کیفیت درخواستی را داشته باشد و اصلاً قابل خرید باشد.
اولین
کاندیدا مناسب‌ترینِ ارزان است، پس رفتار بدون مدل تغییر نمی‌کند.

مکمل‌ها از روابط اعلام‌شدهٔ خودِ فایل می‌آیند، برای زیر‌دسته‌ای *متفاوت*، و مثل
بقیه با اتاق فیلتر می‌شوند. محصول دومِ همان زیر‌دسته «جایگزین» است، هرگز مکمل.

### ۶–۸. استدلال، و چرا اختیاری است

پروژه‌ای که هر نیازش دقیقاً یک کاندیدا دارد **هیچ فراخوانی مدلی ندارد** — ترتیب
قطعی خودش تنها پاسخ ممکن است.

وقتی انتخابی هست، یک فراخوانی برنامه‌ها را می‌گیرد و با یک پیشنهاد پاسخ می‌دهد.
سپس `_validate` هر شناسهٔ محصول را دوباره با مجموعهٔ کاندیداها می‌سنجد. پیشنهادی
که به چیزی اشاره کند که هرگز ارائه نکرده‌ایم، با ذکر دلیل کنار گذاشته می‌شود. مدل
پیشنهاد می‌دهد؛ تصمیم نمی‌گیرد.

| نیازهایی که محصولی در کاتالوگ ندارند | کاشی، عایق‌کاری، لوله‌کشی، روشنایی، رنگ |

توزیع «پیشنهاد به ازای هر محصول» تصویر صادقانه است: یک‌سوم فهرست‌ها هر پنج
فروشنده را دارند و بیش از یک‌سوم فقط یکی. هیچ پُرکردن مصنوعی در جدول فروشنده‌ها
نیست.

`data/raw/` برداشت‌های دست‌نخوردهٔ جست‌وجو و `data/product-pages/` صفحه‌هایی است که
از آن‌ها آمده؛ `scripts/build_catalog.py` آن‌ها را به فایل پالایش‌شده تبدیل و
`scripts/add_offers.py` پیشنهادهای فروشنده را می‌چسباند. هیچ‌کدام ورودی خام را
تغییر نمی‌دهند.

## ۶. تصمیم‌های محصول

تصمیم‌هایی دربارهٔ اینکه محصول *چیست*، در برابر اینکه *چگونه* ساخته می‌شود. هرکدام
تصمیمی است که می‌شد به‌گونه‌ای دیگر گرفت.

**پروژه موضوع اصلی است، نه محصول.** کسی که سرویس بهداشتی را بازسازی می‌کند
فهرست خرید نمی‌خواهد؛ می‌خواهد بداند کار تمام‌شده چقدر هزینه دارد و چه بخرد.
بنابراین جریان پروژه ستون فقرات برنامه است و جست‌وجوی محصول مسیر باریک‌تری است
که به آن خوراک می‌دهد.

**هیچ‌چیز خودبه‌خود وارد لیست انتخاب‌ها نمی‌شود.** پیشنهاد، مشاوره است. پروژه با
لیست خالی شروع می‌شود و یک کلیک آن را پر می‌کند. برای حالت بی‌صبر یک دکمهٔ «انتخاب
همهٔ پیشنهادها» و برای بقیه دکمه‌های تک‌به‌تک هست — اما نقطهٔ شروع همچنان لیست
خالی است.

**نیازی که نمی‌توانیم تأمین کنیم، همچنان نیاز است.** نشان داده می‌شود، نام برده
می‌شود و از برآورد کنار گذاشته می‌شود. هرگز بی‌سروصدا حذف نمی‌شود و هرگز با
«چیزی شبیه به آن» جایگزین نمی‌شود، چون ساختن یک نیاز از اعلام یک شکاف بدتر است.

**در لیست انتخاب‌ها «تعداد» نیست.** حذف شد. تعداد یعنی «این‌قدر بخر»، چیزی که
فروشگاه برای آینه یا شیر‌آلاتی که مجموعه‌ای فروخته می‌شود نمی‌تواند رعایت کند و
کاربر هم هرگز آن را نخواسته. عددی که می‌ماند، تعدادِ نیازِ پروژه است که پرسش
دیگری را پاسخ می‌دهد و می‌ماند.

**یک دکمهٔ بهینه‌سازی، نه دو تا.** ارزیابی دوبارهٔ پروژه و بهینه‌سازی لیست انتخاب‌ها
یک تصمیم‌اند، پس یک دکمه‌اند که هر دو را با مقادیر فرم انجام می‌دهد. بهینه‌سازی
هرگز پرسش را دوباره تفسیر نمی‌کند — تفسیر دوباره باعث می‌شد دکمه دو معنا داشته باشد.

**توضیح‌ها کنار نتیجه، نه پشت یک کلید بازشو.** زبان خودِ فروشگاه اول، دلایل مدل
دوم. محصولی که هیچ‌کدام را ندارد «بدون توضیح» برچسب می‌خورد، نه اینکه خودفرض
نمایش داده شود.

**لیست انتخاب‌ها، نه سبد خرید.** بدون پرداخت، بدون تعداد، بدون «سبد». آنچه هست
فهرستی از چیزهایی است که باید بخرید، و همین نام را دارد.

**هیچ اثبات اجتماعی ساختگی.** بدون امتیاز، بدون تعداد نظر، بدون درصد محبوبیت.
کاتالوگ هیچ‌کدام را ندارد، و دمویی که آن‌ها را می‌سازد درس غلطی دربارهٔ آنچه سیستم
می‌داند می‌دهد.

**فارسی و راست‌به‌چپ پیش‌فرض‌اند، نه یک locale.** `dir="rtl"` همه‌جا، تنها
ویژگی‌های منطقی CSS (`ms-`/`me-`/`ps-`/`pe-`/`start-`/`end-`)، ارقام فارسی در هر عدد
نمایان، `٬` برای جداکنندهٔ هزار، تومان همیشه پس از عدد، و بدون `letter-spacing` روی
متن فارسی.

## ۷. تصمیم‌های فنی

**FastAPI + Pydantic v2 + SQLAlchemy 2 + PostgreSQL، به‌صورت تک‌واحد ماژولار.** یک
واحد استقرار، مرزهای داخلی روشن. کاتالوگ فایل است نه جدول، و این تنها جایی است که
این انتخاب واقعاً سود می‌دهد: داده نسخه‌پذیر، قابل diff و قابل بازبینی است و
واژگانی که تطبیق‌دهنده استفاده می‌کند مستقیم قابل مشاهده است.

**کاتالوگ از دیسک خوانده می‌شود، نه در پایگاه داده.** محصول، قیمت و پیشنهاد چیزی
«داده‌شده» هستند — از توروب برداشت شده — نه چیزی که برنامه مالکش باشد. پایگاه داده
فقط آنچه را نگه می‌دارد که برنامه مالکش است: لیست انتخاب‌ها، تحلیل‌ها، قالب‌ها و
قواعد نیاز. این کار قاعدهٔ «هرگز محصول نساخت» را از نظر ساختاری اجراشدنی می‌کند.

**`extra="forbid"` در همه‌جا.** پایهٔ مشترک `StrictModel` باعث می‌شود تغییر اسکیما
یک تغییر ناسازگار باشد، نه گشادشدن خاموش. همین، سازوکار پشت کل قاعدهٔ محصول است.

**یک قالب‌بندی عدد در فرانت‌اند؛ یک مرجع پول در بک‌اند.** `utils/format.ts` تنها
جایی است که رقم به متن تبدیل می‌شود. بک‌اند هرگز به جمعِ فرستاده‌شده از کلاینت
اعتماد نمی‌کند و هرگز یکی از مدل نمی‌گیرد.

**مدل‌های Pydantic یک‌بار و دستی در `types/api.ts` آینه شده‌اند.** تولید خودکار
نوع‌های کلاینت، یک گام build دیگر می‌بود؛ آینهٔ دستی قابل بازبینی است و `vue-tsc`
ناهماهنگی را هنگام کامپایل می‌گیرد.

**Pinia فقط حالتِ واقعاً مشترک را نگه می‌دارد.** جریان جست‌وجو، حافظهٔ نهان کاتالوگ،
انتخاب‌ها. حالت مخصوص هر کامپوننت، مخصوص خودش می‌ماند.

**Tailwind روی توکن‌های طراحی نگاشت شده و رنگ خودش را تعریف نمی‌کند.**
`theme/material.css` تنها منبع حقیقت است؛ `theme.spec.ts` ساخت را ناکام می‌کند اگر
کامپوننتی رنگ، شعاع، سایه یا مدت زمان را دستی نوشته باشد.

**کلاینت LLM یک ماژول با قرارداد سخت‌گیرانه است.** `chat_json(system, user,
schema_model)` هر پاسخ را اعتبارسنجی می‌کند و «مدل امتناع کرد» را از «مدل وسط
فکرش قطع شد» و از «کلید نیست» جدا می‌کند. دو مورد آخر یک‌بار با بودجهٔ بزرگ‌تر
دوباره تلاش می‌شوند؛ مورد اول نه، چون تکرارِ یک امتناع فقط یک امتناعِ دیگر می‌دهد.

**برای هر تصمیم یک فراخوانی استدلال، و فقط وقتی تصمیمی هست.** هم استدلال پروژه و هم
بهینه‌سازی سبد، نخست کاندیداها را قطعی می‌سازند و از مدل فقط انتخاب یا توجیه
می‌خواهند. `finish_reason=length` خوانده و گزارش می‌شود، نه اینکه به امید پارس شود.

**آزمون‌ها ویژگی را می‌سنجند، نه نمونه.** آزمون‌های نیازها الزام می‌کنند که نیازِ
مبل و نیازِ تخت **فهرست‌های متفاوتی** بدهند، پس یک جدولِ ثابتِ اتاق→نیاز آن‌ها را
از کار انداخته می‌دهد. آزمونی که جوابِ درست را ثابت می‌نویسد، خودش همان باگی است
که باید بگیرد.

## ۱۱. آزمون‌ها

```bash
make test                # همه‌چیز

cd backend  && .venv/bin/python -m pytest -q
cd frontend && npm run test:run && npm run typecheck
```

**بک‌اند — ۶۷۳ آزمون در ۲۸ فایل: ۶۶۶ موفق، ۷ خطای شناخته‌شده.** این خطاها همه در
انتخاب کاندیدای مکمل‌اند و پیش از بقیهٔ این کار وجود داشته‌اند؛ در بخش «محدودیت‌های شناخته‌شده» در انتهای همین سند فهرست شده‌اند، نه اینکه گرد به بالا شوند. حوزه‌هایی که ارزش نام‌بردن دارند:

- ساختار تفسیر و اسکیمای سخت‌گیرانه، از جمله همان باری که پیش‌تر رد می‌شد;
- معنای نیازها به‌صورت ویژگی (مبل و تخت متفاوت‌اند)، هرگز به‌صورت فهرست ثابت؛
- کلمات اتاق شاهد نیستند — رگرسیون بالا، تثبیت‌شده؛
- بهینه‌سازی بودجه هرگز جمع را بالا نمی‌برد و هرگز دو بار مدل را صدا نمی‌زند؛
- مدل هرگز نمی‌تواند محصول بسازد: شناسه‌های ساختگی با دلیل کنار گذاشته می‌شوند؛
- پاسخ یک مدل نمی‌تواند کاندیداهای دامنهٔ دیگر را تحت تأثیر قرار دهد.

**فرانت‌اند — ۱۶۷ آزمون در ۱۳ فایل: ۱۶۴ موفق، ۳ خطای شناخته‌شده** (یک ادعای رنگ
برند در `theme.spec.ts` و دو رشتهٔ توضیح در `views.spec.ts` — هر سه پیش از این کار
بوده‌اند). پوشش شامل استورها، اجزای پایه، تجربهٔ محصول و انتخاب‌ها،
صفحهٔ پروژه و جدول نیازها، thinking states، و نگهبان‌هایی که مطمئن می‌شوند
مفاهیم حذف‌شده حذف‌شده بمانند (تعداد، محصولات مرتبط).

بررسی نوع بخشی از ساخت فرانت‌اند است: `npm run build` اول `vue-tsc` را اجرا
می‌کند، پس خطای نوع به‌جای انتشار، ساخت را ناکام می‌کند.

دو نگهبان ارزش ذکر دارند چون نادر و عمدی‌اند:

- `noQuantityOrRelated.spec.ts` **متنِ** استور و ویوها را می‌خواند و اگر آن واژه‌ها
  برگردند ناکام می‌شود. این یک lint است که به شکل آزمون نوشته شده.
- `theme.spec.ts` اگر کامپوننتی به‌جای توکن، رنگ/شعاع/سایه/مدت را دستی بنویسد
  ناکام می‌شود.

## ۱۲. ساختار پروژه

## ۱۳. محدودیت‌های شناخته‌شده

این‌ها واقعی‌اند و گفتنشان لازم است.

- **کاتالوگ کوچک و ناقص است.** ۷۰ محصول در ۴ دسته. کاشی، عایق‌کاری، لوله‌کشی،
  روشنایی و رنگ **در آن نیست**، پس بازسازی سرویس بهداشتی فقط تا حدی پاسخ‌پذیر
  است. آن نیازها برآورده‌نشده ظاهر می‌شوند که نتیجهٔ صادقانه است، اما یعنی سناریوی
  اصلی دمو آشکارا ناتمام است.
- **کاتالوگ کیفیت را ثبت نمی‌کند.** کیفیت همهٔ محصولات `null` است، پس کیفیت نمی‌تواند
  چیزی را رتبه‌بندی یا محدود کند. API آن را `null` گزارش می‌کند به‌جای حدس‌زدن، و
  انتخاب کاندیدا به قیمت برمی‌گردد. یعنی `quality_min` روی نیاز حمل می‌شود ولی در
  برابر محصولات اعمال نمی‌شود.
- **برآوردها فقط مواد ساختمانی‌اند.** متراژ × قاعده × قیمت کاتالوگ. بدون دستمزد،
  بدون زمان‌بندی، بدون ضایعات، بدون سود پیمانکار. برآورد ساخت نیست.
- **یک پروژه می‌تواند ناقص پوشش داده شود**، و برای دسته‌های بالا خواهد بود.
  `missing_categories` شکاف را گزارش می‌کند و چیزی جایگزینش نمی‌شود.
- **سوابق فروشنده برای هر فهرست جداست و یکسان‌سازی نشده.** ۲۲۵ پیشنهاد از ۱۷۸
  فروشگاه می‌آید چون یک فروشنده در صفحه‌های مختلف با هویت متفاوت تکرار شده. یکسان‌سازی
  درست آن به یک مرحلهٔ تطبیق فروشنده نیاز دارد که این دمو ندارد.
- **ده آزمون قرمز است و این موضوع شناخته‌شده است.** هفت مورد در بک‌اند، همه در
  انتخاب کاندیدای مکمل (`TestProjectComplementary`، `TestReasoningStatusIsReported`،
  و یکی در `test_complementary`): استخر مکمل‌ها جایی خالی برمی‌گردد که پیش‌تر یک
  نگاشتِ نادرستِ آینه‌محور یا نگاشتِ غایب پرش می‌کرد، پس `not_needed` گزارش می‌شود
  در حالی که `ok` انتظار می‌رفت. سه مورد در فرانت‌اند: یک ادعای رنگ برند در
  `theme.spec.ts` و دو ادعای رشتهٔ توضیح در `views.spec.ts`. همه پیش از این مستندسازی
  وجود داشته‌اند و هیچ‌کدام ناشی از آن نیست. آشکارا باقی گذاشته شده‌اند نه skip و نه
  حذف، چون مجموعه‌آزمونی که خطاهایش را پنهان کند دیگر سند نیست.
- **پایبندی به پرامپت، ویژگیِ مدل است نه این کد.** پرامپت سلسله‌مراتب خروجی را صریح
  بیان می‌کند، اما مدلی که پیش از پاسخ روایت کند باز هم می‌تواند بودجهٔ توکن را
  تمام کند و `finish_reason=length` برگرداند. این خطا گزارش می‌شود، نه دور زده.
- **کاندیداهای مکمل با تعداد زیر‌دسته‌های نگاشت‌شده ضرب می‌شوند.** نیازی که به سه
  زیر‌دسته نگاشت می‌شود، برای هر سه مکمل پیشنهاد می‌دهد. درست است، اما پرامپت
  استدلال را بزرگ‌تر از نیاز می‌کند.
- **بدون احراز هویت، بدون پرداخت، بدون پرداخت نهایی.** بدون رابط چندزبانه — برنامه
  فقط فارسی است؛ این README دوزبانه است. بدون رتبه‌بندی یادگیری ماشین.
- **لیست انتخاب‌ها در `localStorage` می‌ماند** و بین دستگاه‌ها هم‌گام نمی‌شود.
- **جست‌وجوی کاتالوگ درون‌فرایندی است** روی یک ستون نرمال‌شده. برای کاتالوگی چند
  مرتبهٔ بزرگ‌تر، جای درستش `pg_trgm` یا یک موتور جست‌وجوست؛ درز اتصالش از پیش در
  `app/catalog/store.py` هست.
